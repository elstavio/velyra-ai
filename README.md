# Velyra AI

Plateforme SaaS d'assistant IA (conversations avec mémoire, documents, agents, workflows, marketplace, API publique, module TikTok), avec essais gratuits, paiements par région (Mobile Money / carte via CinetPay), portefeuille, sécurité renforcée et administration protégée par double authentification.

Construite à partir de votre cahier des charges (`Cahier_des_charges_revise.docx`) et du fichier `texte_3.txt` (scaffold « Velyra AI »). **Lisez la section « Ce qui est testé / non testé » avant toute mise en production.**

## Architecture

| Élément | Choix |
|---|---|
| Backend | Node 22 + TypeScript, **sans framework** (routeur HTTP maison), `node:sqlite` en dev/tests, PostgreSQL en production (paquet `pg`) |
| Frontend | React 19, hash-routing, bundle esbuild, mobile d'abord, en français |
| Dépendances d'exécution | une seule : `pg` |
| Hébergement visé | Render (backend, gratuit) + Neon (PostgreSQL gratuit) + Netlify (frontend, facultatif — le backend sert déjà le frontend) |

Écart avec le scaffold d'origine (NestJS/Next.js/Prisma/Redis/Qdrant/K8s/Terraform/mobile/desktop) : ces briques **ne sont pas** construites. Voir « Non réalisé ».

## Démarrage local (démonstration)

```bash
npm install
npm run build
ADMIN_EMAIL=moi@exemple.com ADMIN_INITIAL_PASSWORD='Un-Mot-De-Passe-Long-2026!' npm start
# http://localhost:3000
```

En dehors de la production : paiements **simulés** (page « Simuler un paiement réussi »), IA en mode démonstration (aucune clé), codes email/SMS affichés dans la console. Tests : `npm test`.

Mot de passe admin : 16 caractères minimum (majuscule, minuscule, chiffre, symbole). L'administration est à `/#/admin/connexion` : mot de passe → configuration de l'application d'authentification (TOTP) → 10 codes de secours affichés **une seule fois** → code email si nouvel appareil/réseau. Après le premier démarrage, **supprimez `ADMIN_INITIAL_PASSWORD`** de l'environnement.

## Déploiement gratuit

1. **PostgreSQL (Neon)** : créez un projet, copiez la chaîne de connexion dans `DATABASE_URL`. Le schéma est créé automatiquement au démarrage.
2. **Clé de chiffrement** : `openssl rand -base64 32` → `ENCRYPTION_KEY`. Conservez-la précieusement : sans elle, les numéros de virement chiffrés sont illisibles.
3. **Backend (Render)** : poussez le dossier sur GitHub, créez un *Web Service* (ou « Blueprint » avec `render.yaml`), renseignez les variables de `.env.example`. `APP_URL` = l'URL https de ce service.
4. **CinetPay** : renseignez `CINETPAY_APIKEY`, `CINETPAY_SITE_ID`, `CINETPAY_SECRET_KEY`, `CINETPAY_TRANSFER_PASSWORD`. URL de notification à déclarer : `APP_URL/api/webhooks/cinetpay` ; retour : `APP_URL/payment/return`.
5. **Frontend séparé (facultatif, Netlify)** : le backend sert déjà l'interface ; si vous préférez Netlify, déployez le dépôt avec `netlify.toml`, définissez `API_BASE` = URL du backend, et mettez l'URL Netlify dans `CORS_ORIGIN` côté backend.
6. **OpenAI** : `OPENAI_API_KEY` (modèles par défaut : `gpt-6.1-sol` pour le chat, `gpt-6-luna` pour les agents ; modifiables via `OPENAI_MODEL`, `SYSTEM_AGENT_MODEL`). Vérifiez ces noms de modèles sur votre compte OpenAI avant production.
6b. **Stripe (Europe : SEPA, Apple Pay, Google Pay, carte)** : `STRIPE_SECRET_KEY`, puis créez un webhook vers `APP_URL/api/webhooks/stripe` (événement `checkout.session.completed` et `checkout.session.expired`) et copiez son secret dans `STRIPE_WEBHOOK_SECRET`. Activez SEPA dans le tableau de bord Stripe. Apple Pay/Google Pay apparaissent dans la page Stripe sur les appareils compatibles.
6c. **Connexion Apple** : créez un *Services ID* chez Apple Developer (compte payant), déclarez votre domaine https et l'URL de retour, puis `APPLE_CLIENT_ID` = ce Services ID. Google : `GOOGLE_CLIENT_ID`. La connexion par code email fonctionne sans configuration (Resend requis).
6d. **Agents quotidiens** : sur Render gratuit le serveur s'endort ; programmez un appel quotidien (ex. cron-job.org, GitHub Actions) : `curl -X POST APP_URL/api/cron/daily -H "x-cron-secret: $CRON_SECRET"`. Au réveil, le serveur rattrape aussi les agents manquants.
6e. **Email/SMS** : `RESEND_API_KEY` (+ domaine d'envoi vérifié) et Twilio. Sans eux, **aucun utilisateur ne recevra de code** : l'inscription est inutilisable en production.
7. Docker : `docker compose up --build` (mode démonstration local avec PostgreSQL).

### Limites des hébergements gratuits (à connaître)
- Render gratuit met le service en veille après inactivité (premier appel lent) et son disque est éphémère : les sauvegardes logiques de l'admin doivent être **téléchargées régulièrement**. La base vit chez Neon, pas sur Render.
- Les **virements automatiques CinetPay** exigent, selon leur documentation, une confirmation par email ou une IP fixe autorisée chez CinetPay ; les IP du palier gratuit de Render sont dynamiques. Tant que ce n'est pas réglé, laissez les virements en pause (les encaissements restent dans le portefeuille admin).
- Le limiteur de débit est en mémoire : valable pour **une seule instance**.

## Ce qui est testé / non testé

**Testé (automatisé)** — 128 tests Node, tous passent (dont : module Social avec faux serveurs TikTok/Google/Meta/WhatsApp, connexion Apple avec faux jeton signé, code email, Stripe avec faux serveur et signature de webhook, requête OpenAI Responses avec faux serveur, 6 agents + superviseur) : hachage/chiffrement/TOTP (vecteurs RFC 6238), inscription et vérifications, essais gratuits (décrément atomique, remboursement en cas d'échec fournisseur), paiements (idempotence, montant/devise incohérents, anti-fraude), portefeuille, virements (reprises, jamais de double envoi automatique), connexion admin 2FA, blocage d'IP, chaîne d'intégrité du journal de sécurité, API publique, conversations/mémoire/documents/agents/workflows/marketplace, TikTok.
**Testé (manuellement, navigateur Chromium, mode démonstration)** : parcours utilisateur complet jusqu'à l'abonnement et connexion/consoles admin, sans erreur JavaScript.
**Testé (partiellement)** : compatibilité PostgreSQL 16 — les ~4 400 requêtes SQL générées par les tests ont été rejouées sur un vrai PostgreSQL 16 sans erreur, **mais pas via le pilote `pg`** du code applicatif.

**Non testé (aucun accès réseau/clés dans l'environnement de construction)** : appels réels à CinetPay (paiement, vérification, virements), Resend, Twilio, Google/Apple Sign-In, Stripe, Anthropic/OpenAI/Mistral (les tests utilisent de faux serveurs : ils vérifient notre code, pas les services réels). Les formats d'API suivent leur documentation publique ; **faites un essai réel en petit montant avant d'ouvrir**. Le code de rejet des virements CinetPay n'est pas documenté : une expression régulière est utilisée par hypothèse.
Le typage TypeScript strict du serveur est vérifié (`tsc`) ; celui du frontend ne l'a pas été (types React indisponibles hors-ligne) — il est couvert par le test navigateur.

## Choix et hypothèses à valider
- **Essais gratuits** : 5 tâches, réservées aux comptes avec email **et** téléphone confirmés (un compte par numéro) — interprétation de votre cahier des charges.
- **Prix** : exemples (Pro : 5 000 XOF/XAF, 15 000 CDF, 80 000 GNF, 9 USD ; TikTok Pro : 3 000 XOF…). Modifiez-les dans Admin › Offres et prix (multiples de 5 hors USD, exigence CinetPay).
- **Recherche de documents** : lexicale BM25, pas sémantique (pas d'embeddings ni Qdrant).
- **« IA » d'analyse admin** : règles statistiques (écarts-types, ratios) sur agrégats anonymes ; toute proposition exige votre validation.
- **TikTok** : uniquement données saisies/CSV, aucune API TikTok, aucune tendance de marché, aucune promesse de résultat.
- **Fraude** : détection par règles, signalement pour décision humaine ; jamais de blocage automatique d'un compte ni de VPN.
- **Droit/conformité** : la conservation des journaux de connexion (180 jours) et des paiements après suppression de compte est une hypothèse à faire valider par un juriste local (protection des données, ARTCI en Côte d'Ivoire notamment).

## Réseaux sociaux et agent « Créateur de contenu » (offre payante « Velyra Social »)
**Ce que fait la version actuelle** : l'abonné Social connecte ses comptes (TikTok, YouTube, Facebook Pages, Instagram professionnel par OAuth ; WhatsApp Business en saisissant l'identifiant du numéro et un jeton Meta), le serveur lit ses statistiques (abonnés, vues, publications récentes) en **lecture seule**, puis l'agent « Créateur de contenu » (Réseaux › Studio) produit plans de contenu, idées, scripts, légendes, messages de vente et analyses à partir de ces vrais chiffres, pour créateurs ou commerçants. Les jetons sont chiffrés (AES-256) ; la déconnexion les supprime et révoque l'accès chez TikTok/Google.
**Ce qu'elle ne fait pas** : aucune publication automatique, aucun envoi de message WhatsApp, aucune promesse de revenus. Ces fonctions exigent des autorisations supplémentaires validées par chaque plateforme (par ex. `video.publish`, `instagram_content_publish`, `youtube.upload`), à ajouter plus tard.
**À faire par vous (obligatoire, rien ne marche sans)** : créer une application développeur chez TikTok (developers.tiktok.com), Google (console Cloud, API YouTube Data), Meta (developers.facebook.com, type Business), y déclarer l'URL de retour `APP_URL/api/social/callback/<plateforme>`, renseigner les clés (`.env.example`), puis **faire valider l'application** par chaque plateforme (revue d'application, politique de confidentialité en ligne). Avant validation, seuls les comptes « testeurs » que vous déclarez peuvent se connecter. Instagram : compte professionnel relié à une Page Facebook (comptes personnels non pris en charge). WhatsApp : jeton d'utilisateur système créé dans Meta Business.
Prix de l'offre Social (exemples à ajuster) : 9 000 XOF/XAF, 27 000 CDF, 144 000 GNF, 15 USD, 14 EUR pour 30 jours, Pro inclus.

## Agents IA internes
Cinq agents (Sentinelle sécurité, Comptable paiements, Ingénieur fiabilité, Modérateur marketplace, Analyste croissance) analysent chaque jour des agrégats anonymes ; un sixième, le Superviseur, ne fait aucun travail métier : il vérifie que les cinq ont tourné, contrôle la forme de leurs résultats, recalcule un chiffre-clé de chacun, relance une fois un agent défaillant et vous alerte. Ils ne modifient jamais comptes, paiements ou contenus : ils proposent, vous validez (Admin › Agents IA). « Se met à jour chaque jour » = analyses et seuils recalculés quotidiennement avec rattrapage ; ce n'est pas un réentraînement de modèle.

## Sécurité renforcée (DDoS/DoS, piège anti-intrusion, confirmation des retraits)
- **Anti-DDoS/DoS** : limite de débit par IP à trois niveaux (rafale très courte avec blocage automatique au-delà d'un volume massif, débit par minute, timeouts HTTP anti-slowloris sur les en-têtes/la requête/le keep-alive), en plus de la limite déjà en place par endpoint sensible (connexion, OTP, webhooks). Testé manuellement en conditions réelles (hors tests automatisés, qui désactivent ce seuil pour ne pas se bloquer eux-mêmes) : au-delà de 15 requêtes/2 s depuis une même IP → ralenti (429) ; au-delà de 60 → bloqué (403) pendant 1 h. À adosser, en production, à un pare-feu/CDN en amont (Cloudflare ou équivalent) pour l'absorption volumétrique, qu'un serveur applicatif seul ne peut pas garantir contre un DDoS distribué de grande ampleur.
- **Piège anti-intrusion (« honeypot »)** : des routes qui n'existent dans **aucune** interface légitime de Velyra (ex. `/api/admin/export-wallet-keys`) sont exposées sciemment. Un utilisateur normal ne peut jamais y tomber ; un balayage ou une tentative d'intrusion, si. Dès qu'une requête les touche : l'IP est bloquée immédiatement (sans attendre de seuil), une alerte critique part sur-le-champ (email + SMS), et une réponse plausible mais entièrement fictive est renvoyée (aucune vraie donnée n'est jamais exposée ni modifiée). Les informations techniques captées (IP, user-agent, chemin visé) sont conservées séparément du journal de preuves et **purgées automatiquement après 10 jours par défaut (réglable via `HONEYPOT_RETENTION_DAYS`)** ; le journal de sécurité chaîné, lui, garde une trace légère de l'incident indéfiniment (preuve en cas de litige). **Ce mécanisme ne contacte jamais l'appareil de l'intrus, n'y affiche rien et n'y exécute rien** (exigence explicite du commanditaire) : il se contente de répondre à ses propres requêtes, comme toute page web. Admin › Sécurité › « Piège & intrusions ».
- **Alerte nouvel appareil/IP** : à chaque connexion réussie d'un utilisateur, l'empreinte d'appareil (en-tête `X-Device-Id` envoyé par le frontend) est comparée à celles déjà connues pour ce compte. Si c'est la première fois, l'utilisateur reçoit immédiatement un email l'invitant à vérifier que c'est bien lui. **Limite assumée** : une adresse IP seule ne permet pas, de façon fiable, de distinguer un VPN légitime d'une IP dynamique opérateur ; une détection VPN fiable demanderait un service tiers payant d'intelligence IP (non intégré par défaut, aucune clé de ce type n'étant disponible dans cet environnement).
- **Confirmation obligatoire par email pour tout retrait** : qu'il parte automatiquement après un paiement ou qu'il soit relancé manuellement depuis Admin › Portefeuille, **aucun transfert n'est exécuté** sans qu'un lien à usage unique envoyé par email (valable 24 h par défaut, réglable via `PAYOUT_CONFIRM_TTL_HOURS`) ait été cliqué. Tant que ce n'est pas fait, les fonds restent dans le wallet. Visible et suivable dans Admin › Sécurité › « Retraits à confirmer ».
- **Passkeys / WebAuthn pour l'administration** : en plus du mot de passe + TOTP + codes de secours déjà en place, un administrateur peut enregistrer une clé de sécurité (Face ID, Touch ID, Windows Hello, YubiKey…) depuis Admin › Sécurité › « Clés de sécurité ». Implémentation **zero dépendance** (décodeur CBOR et vérification de signature ECDSA P-256 écrits pour ce projet, via `node:crypto`), restreinte par choix à l'algorithme ES256 et à l'attestation « none » (voir le commentaire dans `server/lib/webauthn.ts` pour la justification). Détection de clonage par compteur de signatures. Testée de bout en bout avec une vraie paire de clés ECDSA générée dans les tests (pas une simulation superficielle).
- **Coffre-fort de secrets (statut uniquement)** : Admin › Système liste les ~15 secrets connus de l'application (clé de chiffrement, clés de paiement, jetons SMS/email, clés IA…), indique s'ils sont présents, et permet de déclarer qu'une rotation vient d'être faite chez l'hébergeur. **Les valeurs elles-mêmes ne sont ni stockées ni affichées par cette page** : la rotation réelle d'une clé se fait toujours dans les variables d'environnement de l'hébergeur (Render ou autre) — c'est un tableau de bord de statut, pas un vrai coffre-fort (HashiCorp Vault, AWS Secrets Manager…), qui n'a pas sa place dans une architecture mono-processus zero-dépendance.
- **WAF logiciel (structurel, pas de filtrage de contenu)** : chaque corps JSON entrant est validé avant traitement (`server/lib/waf.ts`) — rejet des clés de pollution de prototype (`__proto__`, `constructor`, `prototype`) à toute profondeur, imbrication excessive, tableaux/objets disproportionnés. **Délibérément restreint à la structure**, jamais au contenu : Velyra est un assistant IA où du texte libre (messages, documents, mémoires, invites d'agent) doit légitimement pouvoir contenir du code ou du SQL sans être bloqué à tort.
- **Sauvegardes chiffrées au repos** : les sauvegardes (`ops.ts`) sont désormais chiffrées AES-256-GCM après compression (`.json.gz.enc`), avec détection d'altération (étiquette d'authentification). Testé : contenu non lisible en clair, falsification de l'en-tête détectée et rejetée, restauration fonctionnelle. Lecture rétrocompatible des anciennes sauvegardes non chiffrées.
- **Analyse de composition logicielle (SCA)** : `npm run security:audit` exécute `npm audit` et rapporte honnêtement le résultat — **y compris quand il ne peut pas vérifier** (pas d'accès réseau au registre npm ou pas de fichier de verrouillage), plutôt que d'annoncer à tort « aucune vulnérabilité détectée ».
- **Détection comportementale par corrélation + réponse automatisée bornée** : si une même IP cumule plusieurs catégories différentes de signal suspect (sondage de chemin, échec de connexion, échec de clé de sécurité, échec 2FA admin) en moins de 10 minutes, elle est traitée comme une attaque probable et bloquée automatiquement — règles explicites et déterministes, **pas un modèle de machine learning**. Toute IP bloquée (par ce mécanisme ou tout autre) entraîne la révocation immédiate de toute session encore active depuis cette IP (confinement). Cette réponse automatisée reste strictement bornée : elle ne touche jamais aux comptes, à l'argent ni aux droits d'un utilisateur, et aucune IA ne peut l'étendre ou s'auto-accorder un privilège — voir `server/services/security.ts`.
- **Zero Trust : revérification continue de la session admin** : une session administrateur n'est plus acceptée « par défaut » une fois ouverte — à **chaque requête**, le serveur vérifie que l'empreinte d'appareil envoyée correspond toujours à celle de l'ouverture de session (sinon révocation immédiate, jeton probablement volé) et qu'aucun blocage d'IP n'est intervenu entre-temps (la session est alors révoquée aussi, pas seulement « gelée » tant que le blocage dure). Un simple changement de réseau (même appareil, IP différente — ex. passage wifi → 4G) est journalisé mais n'entraîne pas de déconnexion automatique, pour ne pas pénaliser un usage légitime.

## Mapping honnête des 15 systèmes de sécurité et de l'architecture « Extra Large » demandés
Un document complémentaire a demandé 15 systèmes de sécurité de niveau entreprise, une architecture distribuée « Extra Large » (passerelle API, orchestration, cache distribué, moteur de recherche, configuration centralisée, tolérance de panne, observabilité multi-environnements) et un moteur central d'orchestration IA multi-fournisseurs. Choix assumé, validé avec le commanditaire : **construire un sous-ensemble réellement opérationnel et vérifiable plutôt que des mécanismes cosmétiques**, et documenter honnêtement ce qui ne l'est pas, plutôt que de prétendre livrer une architecture que l'environnement (projet zero-dépendance, mono-processus Node, hébergement gratuit, sans accès réseau sortant dans cet environnement de construction) ne permet pas de construire sincèrement.

| # | Système demandé | État | Détail |
|---|---|---|---|
| 1 | Passkeys FIDO2/WebAuthn + MFA + authentification admin durcie | **Fait** | Passkeys (ES256, zero dépendance, testé de bout en bout) en complément de TOTP + codes de secours + confirmation email déjà en place. |
| 2 | Architecture Zero Trust | **Partiel** | Revérification continue de la session admin (IP/appareil) à chaque requête, ci-dessus. Ce n'est pas un maillage réseau Zero Trust complet (pas de mTLS entre services : il n'y a qu'un seul processus serveur). |
| 3 | WAF (pare-feu applicatif) | **Partiel** | Garde structurelle logicielle contre la pollution de prototype et les abus de structure JSON. Pas de filtrage de contenu par signatures (incompatible avec un assistant IA qui doit accepter du texte libre), pas de WAF matériel/CDN — recommandé en amont (Cloudflare ou équivalent). |
| 4 | Chiffrement avancé + gestion des clés | **Partiel** | AES-256-GCM pour les secrets sensibles en base et les sauvegardes ; clé de chiffrement lue depuis l'environnement. Pas de KMS/HSM dédié avec rotation automatique — hors de portée d'un hébergement gratuit mono-processus. |
| 5 | IDS/IPS | **Partiel** | Détection d'intrusion applicative (honeypot, sondage de chemins, corrélation comportementale) + blocage automatique = IDS/IPS au niveau applicatif. Pas d'inspection réseau bas niveau (type Suricata/Snort). |
| 6 | Anti-DDoS avancé | **Partiel** | Limitation de débit multi-niveaux + timeouts anti-slowloris, testés manuellement en conditions réelles. L'absorption volumétrique d'un DDoS distribué de grande ampleur exige un CDN/pare-feu en amont, qu'un serveur applicatif seul ne peut pas garantir. |
| 7 | Protection API avancée (validation, autorisation serveur, limitation) | **Fait** | Validation systématique des champs (`lib/util.ts`), autorisation vérifiée côté serveur sur chaque route (`route.auth`, jamais déduite d'une donnée cliente), limitation de débit à plusieurs niveaux. |
| 8 | Détection comportementale des menaces assistée par IA | **Fait (honnête sur la méthode)** | Corrélation par règles explicites sur les événements de sécurité, ci-dessus. **Ce ne sont pas des règles apprises par un modèle d'apprentissage automatique** — le qualificatif « IA » serait trompeur ici ; les agents IA existants (voir plus bas) ne font que proposer, jamais agir seuls. |
| 9 | Réponse automatisée aux incidents (révocation, confinement, alertes) | **Fait** | Révocation automatique et bornée des sessions liées à une IP bloquée, alertes immédiates. Jamais d'auto-élévation de privilèges IA, jamais d'action sur l'argent ou les comptes sans confirmation humaine. |
| 10 | Coffre-fort de secrets centralisé avec rotation | **Partiel** | Tableau de bord de statut + déclaration de rotation, ci-dessus. Les valeurs réelles restent dans les variables d'environnement de l'hébergeur : un vrai coffre-fort (Vault…) est un service à part entière, hors de portée zero-dépendance. |
| 11 | Confidentialité et isolation des données | **Fait** | Isolation par utilisateur déjà appliquée à chaque requête de données (filtrage par `user_id` côté serveur) ; chiffrement AES-256 des jetons sociaux et des sauvegardes. |
| 12 | Surveillance continue / journalisation type SIEM | **Partiel** | Journal de sécurité chaîné par hachage (infalsifiable, vérifiable), tableau de bord Admin › Sécurité. Pas de SIEM centralisé multi-hôtes (Elastic/Splunk) : il n'y a qu'un seul hôte applicatif à surveiller. |
| 13 | Sécurité de pipeline SAST/SCA/DAST | **Partiel** | SCA réelle (`npm audit`, honnête sur ses limites d'environnement). Pas de SAST (ex. Semgrep) ni de DAST automatisés : aucune intégration continue (CI) n'existe dans ce projet pour les y brancher — à ajouter avec GitHub Actions si souhaité. |
| 14 | Sauvegardes chiffrées, isolées et résistantes à l'altération, avec restauration testée | **Fait** | AES-256-GCM avec détection d'altération, restauration testée automatiquement. L'isolement géographique/l'immuabilité dépend du stockage choisi côté hébergeur (hors du code applicatif). |
| 15 | Coordination de défense multi-couches adaptative | **Partiel** | Les couches (limitation de débit, honeypot, corrélation comportementale, blocage automatique, révocation de session, Zero Trust admin) partagent déjà le même journal chaîné et les mêmes alertes. « Adaptatif » = seuils recalculés par règles, pas par apprentissage automatique. |
| — | Architecture distribuée « Extra Large » (passerelle API, cache distribué, moteur de recherche, config centralisée, tolérance de panne multi-nœuds) | **Non réalisée** | Contraire au choix de conception documenté dès l'origine (zero dépendance, mono-processus) et à l'hébergement gratuit visé. La construire sincèrement demanderait Redis, Kubernetes, un vrai moteur de recherche distribué (Elasticsearch/Qdrant) et plusieurs services réseau — c'était déjà listé dans « Non réalisé » avant cette demande. |
| — | Moteur central d'orchestration IA multi-fournisseurs | **Fait (existant)** | Le routeur multi-fournisseurs (Anthropic/OpenAI/Mistral, bascule en cas d'échec) existait déjà. Contraintes de sécurité demandées déjà respectées par construction : l'IA ne peut jamais s'auto-accorder un privilège ni contourner l'autorisation côté serveur (`route.auth` est vérifié indépendamment de tout ce qu'un modèle IA produit), ne voit jamais les données d'un autre utilisateur sans y être explicitement autorisée par le code, et toute proposition d'agent reste `pending` jusqu'à une décision humaine explicite (testé, voir `test/behavior.test.ts`). |
